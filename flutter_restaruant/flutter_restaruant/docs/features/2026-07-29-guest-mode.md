# 功能規格：訪客模式 (Guest Mode)

## 1. 功能目標與背景 (Why)

目前 App 的登入是**硬性門檻**：`SplashPage` 無條件導向 `SignInPage`，使用者在還沒看到任何一間餐廳之前，就被要求交出帳號。對一個「找餐廳」的工具型 App 來說，這是最糟糕的第一印象——使用者尚未理解產品價值，就被要求付出成本。

本功能提供「先瀏覽、後登入」的路徑：未登入者可自由使用搜尋、餐廳列表與餐廳詳情，只有在觸及**需要帳號綁定的功能**（最愛）時，才引導其登入。

### 為什麼「最愛」必須被擋在 UI 層

這是**體驗與流程**需求：讓未登入者能先瀏覽，並在需要帳號的動作上被導向登入頁。

### 關於資料層的 uid 退化（已查證，非本次要解的問題）

`FavorDataSource`（`lib/data_layer/datasources/favor_data_source.dart`）以下列方式解析使用者：

```
String get _uid => SignInManager().accountDto?.uid ?? '';
```

理論上 `accountDto` 為 null 時 `_uid` 會退化為空字串。但**這在本功能的設計下不會被觸發**：訪客點擊最愛按鈕時，UI 層在發出 `ToggleFavor` 之前就導向登入頁，bloc → repository 這條路徑根本不會進入，`_uid` 也就不會被解析。

已查證的事實（`grep` 全 codebase 的 `ToggleFavor` 派發點）：

- **全專案只有一個最愛派發點**：`lib/component/cell/restaurant_detail/restaurant_head_cell.dart:38`
- `MainBloc` 雖有 `ToggleFavor` event / state / handler，但**沒有任何 UI 派發它**；`RestaurantItemCell` 沒有最愛按鈕。該路徑目前是無法從 UI 到達的死碼。
- `MainBloc` 本身不使用 `SignInManager` 的任何登入資訊。

因此本規格**不設立「防止空 doc id 寫入」的驗收條件**——那會是在為一條不存在的路徑寫防禦。只要維持「按鈕先導向登入頁」這個單一攔截點，問題就不會發生。

## 2. 使用者故事 (User Stories)

### US-1：訪客進入 App 瀏覽
> 身為一個還不想註冊的新使用者，我想直接進入 App 搜尋與瀏覽餐廳，以便先判斷這個 App 對我有沒有用。

登入頁三方登入按鈕（Google / Apple）下方有一個明確的「訪客模式 / Continue As Guest」按鈕。點擊後直接進入 `MainPage`，可正常使用搜尋、篩選、地圖/列表切換、開啟餐廳詳情。

### US-2：訪客重啟 App
> 身為已選擇訪客模式的使用者，我不想每次開 App 都要重新點一次「訪客模式」。

訪客狀態被持久化。App 重啟後 `SplashPage` 讀取旗標，直接進入 `MainPage`，**跳過登入頁**。

### US-3：訪客點擊最愛按鈕
> 身為訪客，當我想收藏一間餐廳時，我期待 App 明確告訴我這需要登入，而不是靜默失敗或假裝成功。

在餐廳詳情頁點擊最愛按鈕，**不執行任何收藏動作**，直接導向登入頁。

### US-4：訪客進入設定頁
> 身為訪客，我沒有帳號可以登出，也沒有帳戶可以刪除；但我想知道要去哪裡建立帳號。

設定頁隱藏「登出」與「刪除帳戶」，改為顯示「登入 / 註冊」按鈕，點擊後導向登入頁。

### US-5：訪客轉為正式登入
> 身為一個決定要註冊的訪客，我完成登入後，App 應該把我當成正式使用者對待。

任何成功的登入/註冊（含 Google、Apple、Email、自動登入）都會**清除訪客旗標**。此後設定頁恢復顯示「登出 / 刪除帳戶」，最愛功能正常運作，重啟 App 不再被視為訪客。

## 3. 驗收條件 (Acceptance Criteria)

### AC-1：登入頁的訪客模式入口
- [ ] `SignInPage` 的三方登入按鈕區塊（`show3rdSignInUpBtns()`）**最底下**新增一個訪客模式按鈕。
- [ ] 按鈕文字走多語系：`intl_zh_TW.arb` 為「訪客模式」、`intl_en.arb` 為「Continue As Guest」，並透過 `S.current.<key>` 取用。
- [ ] 該按鈕在 iOS 與 Android **皆顯示**（不同於 Apple 登入按鈕僅限 iOS）。
- [ ] 點擊後：標記為訪客狀態 → 導向 `MainPage`，且不得留下可返回登入頁的堆疊（比照既有 `pushReplacementNamed` 行為）。

### AC-2：訪客狀態的持久化與判定
- [ ] 訪客狀態以 SharedPreferences 持久化，key 命名遵循既有 `Constants.prefKeyAccountInfo` 慣例，集中定義於 `lib/utils/constants.dart`。
- [ ] 全 App 存在**單一**「目前是否為訪客」的判定來源；各頁面不得各自讀取 SharedPreferences 判斷。
- [ ] 「訪客」與「已登入」為互斥狀態：`SignInManager().accountDto != null` 時，一律不視為訪客。
- [ ] 不新增任何 pubspec 依賴（`shared_preferences: ^2.2.0` 已存在）。

### AC-3：Splash 啟動分流
- [ ] `SplashPage` 在既有的延遲後，依訪客旗標分流：
  - 旗標為 true → `pushReplacementNamed(MainPage.routeName)`
  - 旗標為 false 或不存在 → 維持現行行為，導向 `SignInPage`
- [ ] 分流不得移除既有的 `mounted` 檢查。
- [ ] 進入 `MainPage` 的路徑必須完成該頁所需的 Bloc/依賴注入，與從登入頁進入時**行為一致**（不得出現只有訪客路徑才會崩潰的情形）。

### AC-4：餐廳詳情頁的最愛按鈕攔截
- [ ] `RestaurantHeadCell` 的最愛按鈕在訪客模式被點擊時，**不發出** `ToggleFavor` 事件。
- [ ] 改為導向 `SignInPage`。
- [ ] 導向後，最愛圖示的視覺狀態**不得**改變（不得出現「先變成已收藏再跳頁」的假成功）。
- [ ] 非訪客（已登入）時，行為與現況完全相同——這是不可退讓的相容性要求。

### AC-5：設定頁的區塊切換
- [ ] 訪客模式下，`createLogoutSection()` 產出的「登出」按鈕與「刪除帳戶」文字連結**皆不顯示**。
- [ ] 訪客模式下，於原位置顯示「登入 / 註冊」按鈕，文字走多語系（zh_TW / en 皆需提供）。
- [ ] 點擊「登入 / 註冊」導向 `SignInPage`。
- [ ] 非訪客時，設定頁畫面與現況完全相同。
- [ ] 「版本資訊」等其他設定項目在兩種狀態下皆正常顯示。

### AC-6：訪客轉正式登入時清除旗標
- [ ] 任何成功登入或註冊後，訪客旗標必須被清除。涵蓋 Google、Apple、Facebook、Email 登入、Email 註冊、自動登入（`AutoSignInEvent`）與生物辨識登入等**所有**成功路徑。
- [ ] 清除點必須是**收斂的單一位置**，不得在每個登入按鈕的 callback 各寫一次。
- [ ] 驗證情境：訪客模式 → 設定頁點「登入 / 註冊」→ 完成 Google 登入 → 設定頁顯示「登出 / 刪除帳戶」→ 殺掉 App 重啟 → 直接進入 `MainPage` 且**以正式帳號身分**（最愛可正常使用）。

### AC-7：正式使用者登出後的狀態
- [ ] 正式使用者執行「登出」後，**不得**被誤判為訪客；應回到登入頁，且重啟 App 後仍停留在登入頁。

### AC-8：測試
- [ ] 訪客狀態的判定與持久化（設定、讀取、清除）具備單元測試。
- [ ] 「登入成功後訪客旗標被清除」具備單元測試。
- [ ] 測試資料與測試邏輯分離（比照專案慣例，置於同檔案的 `_Data` 類別）。

## 4. 範圍邊界 (Out of Scope)

### 明確不做

- **不修改 Firestore 安全規則**。本次僅在 App 端攔截，後端規則的加固另案處理。
- **不做訪客資料遷移**。訪客不產生任何最愛資料，因此登入後沒有東西需要合併或搬移。
- **不做本機端的訪客最愛**。不提供「訪客的最愛存在本地、登入後再上傳」這條路——那是另一個功能，且會直接引入 US-5 的資料合併衝突。
- **不新增依賴**、**不引入新的狀態管理套件**、**不重構 `SignInManager` 的既有登入流程**。
- **不修改 `FavorDataSource` 的 uid 解析邏輯**。本次以 UI 層攔截為準；`?? ''` 的退化行為留待安全規則加固時一併處理（見風險 R-1）。
- **不改動登入頁既有的 Email / Google / Apple 登入流程與版面**，僅在三方按鈕區塊末端追加。

### 其他最愛進入點的處理範圍

已 `grep` 全 codebase 確認最愛的實際進入點，界定如下：

| 進入點 | 位置 | 本次範圍 |
|--------|------|----------|
| 餐廳詳情頁最愛按鈕 | `RestaurantHeadCell:38` | **要做**，導向登入頁（AC-4）。這是全專案**唯一**的 `ToggleFavor` 派發點 |
| `MainBloc` 的 `ToggleFavor` | `main_bloc.dart:67` | **不做**。event / state / handler 雖存在，但無任何 UI 派發它，`RestaurantItemCell` 也沒有最愛按鈕——這是從 UI 無法到達的死碼。為它加訪客判斷等同為不存在的路徑寫防禦。若未來真的加了列表最愛按鈕，屆時比照 AC-4 在該按鈕上攔截即可 |
| 抽屜選單「口袋名單」→ `FavorPage` | `MainPage` 抽屜項目 | **本次不隱藏、不移除**。訪客點進去會看到空清單，屬可接受行為。是否改為導向登入頁，列為待確認事項 Q-1 |

## 5. 風險與待確認事項

### 風險

- **R-1（低）**：`FavorDataSource._uid` 的 `?? ''` 退化在程式碼中仍然存在。目前不會被觸發（唯一的最愛入口已在 UI 層攔截），但若未來新增最愛入口而忘記比照 AC-4 攔截，該退化才會浮現。緩解方式是把訪客判定收斂為單一來源（AC-2），讓新入口容易沿用同一個判斷。
- **R-2（相容性，中）**：`SplashPage` 目前只導向 `SignInPage`，`MainPage` 從未被當作啟動後的第一個畫面。需確認 `MainPage` 所依賴的 Bloc 與初始化不隱含「剛從登入頁過來」的前提，否則訪客路徑會出現只在該路徑發生的崩潰（AC-3 已納入驗收）。
- **R-3（狀態一致性，中）**：訪客旗標與 `SignInManager().accountDto` 是兩份狀態，存在不同步的可能（例如登入成功但旗標未清）。AC-2 的互斥規則與 AC-6 的單一清除點即為此而設。
- **R-4（低）**：`SignInPage.initState` 會發 `AutoSignInEvent()`。訪客從設定頁進入登入頁時，若自動登入成功，會直接跳往 `MainPage`。此行為與現況一致，屬可接受，但需確認此路徑同樣觸發旗標清除（涵蓋於 AC-6）。

### 待確認事項

- **Q-1**：訪客點抽屜選單的「口袋名單」，是進入空的 `FavorPage`，還是直接導向登入頁？本規格暫定為**進入空清單**（維持現狀，改動最小）。若希望一致地引導登入，需明確指示。
- **Q-2**：訪客從最愛按鈕被導向登入頁並**完成登入後**，是否要自動返回原本的餐廳詳情頁？本規格暫定**不做**——比照既有登入成功的行為導向 `MainPage`。若要保留返回點，屬額外的路由狀態傳遞需求。
- **Q-3**：訪客模式按鈕是否需要二次確認或功能限制說明（例如「訪客無法使用收藏」的提示）？本規格暫定**不做**。
